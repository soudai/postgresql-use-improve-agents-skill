# テーブル設計とリファクタリング候補を調べる

[English](../en/04-schema-review.md) · [ユースケース一覧](README.md)

架空のシナリオとレポート例です。実DBを診断した結果や、
スクリプトの出力をそのまま掲載したものではありません。

## シナリオと提供する証拠

注文サービスで整合性を確認し、独立した業務操作が `app.orders` の
変更可能な状態を共有しすぎていないか調べます。提供資料は同じ
PostgreSQL 18 環境と同じデプロイを対象にしています。

| 利用者が提供する入力 | 主な証拠 |
| --- | --- |
| `orders-schema.json` | snapshot v2。テーブル・列・制約の収集は打切りなく完了し、通常継承子はない。`customer_id` から `app.customers(id)` へのFKはない。domainにはNOT NULLがあるが、`column_not_null=false`。 |
| `orders-contract.json` | 出典付きの設計契約。注文には既存顧客が必須。発行済み請求書の事実は不変だが、注文の現在状態は更新可能。決済と配送では更新者とライフサイクルが異なる。 |
| `orders-evidence.json` | 範囲を明示した集計で、確認した1,000行中2行の顧客IDがNULL。発行後に請求金額をUPDATEした実行traceがある。決済・配送のtraceを対応付け、同一注文キー、blocker chain、transaction境界と600 msの待機を確認。 |
| `order-glossary.md` | 合意した列名は `shipping_status`。catalogとアプリは `shiping_status` を使用。 |

この例の集計とtraceは、2026-11-06の01:00–01:05 UTCを対象とします。
この時間帯以外の問題発生頻度までは分かりません。
契約には、`cancelled_at` はキャンセルまで未設定でよいこと、
`email_opt_in` は独立した真偽属性であることも記録されています。

ファイル名は、自分で用意するexportや設計資料の仮名です。
同名の入力ファイルは、この例に同梱していません。契約と観測情報には
元資料の参照先と観測時刻を残してください。

## コピーして使うプロンプト

```text
$postgres-schema-review

提供した orders-schema.json、orders-contract.json、
orders-evidence.json、order-glossary.md を使って app.orders をレビューしてください。

契約違反の確定、リファクタリング候補、証拠不足、意図した例外を分けてください。
FK、列とdomainのNOT NULL、命名、ライフサイクル、責務、確定済み事実を確認し、
NULL・boolean・更新可能な行を一律に問題としないでください。

決済・配送の書込みを、提供した同一キーのblocker traceと対応付けてください。
関連するライフサイクル・責務・競合の指摘を一つの改善テーマにまとめ、
それぞれの証拠を残してください。分割とtransaction短縮・更新順序変更を比較してください。

対象範囲、重要度、確度、根拠、改善案、検証方法を報告してください。
互換性、多重度、RLS、切戻しも含め、提供済みの証拠からレポートと移行計画案を作成してください。
```

## 結果の記載例

| 指摘 | 判定 | 根拠と影響 |
| --- | --- | --- |
| 顧客へのFKがない | `confirmed` | 全件収集した制約と、出典付きの同一DB内の関連契約が一致しない。孤児行の件数は未確認。 |
| 必須の顧客ID | `confirmed` | domain NOT NULLは列全体の保証ではない。範囲付きの集計でも契約違反を2行確認。 |
| 発行後に請求書の事実を更新 | `confirmed` | 契約と発行後のUPDATE観測が同じ事実を指す。静的なUPDATEコードだけでは実行の証明にならない。 |
| 決済・配送の状態が混在 | `candidate` | 更新者とライフサイクルの違い、対応付けた600 msの同一キー待機から分割を検討する。すべての待機の原因とは断定しない。 |
| `shiping_status` の綴り | `confirmed` | 用語集で期待する名称が分かる。優先度は互換性への影響も踏まえて決める。 |

`cancelled_at`、`email_opt_in`、変更可能な現在の業務状態は、
NULL・flag・不変性を一律に要求することへの、理由付きの例外として残します。
列数や `updated_at` の存在だけで再設計を決めません。

改善案では、発行済み請求書の事実を変更可能な注文状態から分離し、
決済試行と配送は実際の多重度に合わせて扱います。再決済や分割配送が
あるため、単純な1対1分割とは限りません。訂正イベントと保存期間にも合意が必要です。

## 次に確認すること

1. FK計画の前に、孤児行、キーの型、参照先の一意性、削除動作、
   tenantキーの有無を確認します。子側索引は別の性能調査として評価します。
2. 確認済みのNULL 2行を修復し、残りの必須性の適用範囲を調べます。
   実サーバ版に合う列制約の強制・検証を計画します。domain制約や
   NULL推定値がゼロであることは、この確認の代わりになりません。
3. 請求書の訂正とすべての更新者を追跡します。同じ業務操作で、
   transaction短縮と分割の待機時間、p95/p99、再試行を比較します。
4. 使い捨て環境で多重度、原子的に守る業務条件、訂正履歴、
   正当な操作の成功と禁止操作の拒否を確認します。
5. 新旧アプリの共存とbackfillを計画します。新構造で受け付けた書込みの
   保持を含めて切戻しを評価し、VALIDATE後に再収集します。
   未検証の制約を追加した段階では完了としません。

# 遅いSQLと索引の仮説を調べる

[English](../en/01-slow-query.md) · [ユースケース一覧](README.md)

架空の入力に基づくレポート例です。実環境の測定結果やコマンドの出力そのものではありません。
以下のファイル名は入力の例です。プロンプトを使う際は自身の環境のエクスポートを用意してください。
これらの入力ファイルは同梱していません。

## 状況と提供する根拠

PostgreSQL 18を使う注文検索APIが、繁忙時の10分間に応答時間の目標を超えています。
提供された統計と取得済み実行計画から調査を始めます。

| 根拠 | 提供値 |
| --- | --- |
| アプリの応答時間 | アプリの計測でp95 420 ms。目標はp95 ≤ 200 ms |
| 統計の観測窓 | 600秒。同じinstance・DB・role・起動時刻で、resetやentryの追い出しはない |
| 対象SQLの差分 | 900 calls、`total_exec_time` 180,000 ms |
| 全top-level SQL | 同じ区間の`total_exec_time`差分は300,000 ms |
| テーブル・索引 | `public.orders`は1,000,000行。索引は`id`の主キーのみ |
| 取得済みスキャンノード | Seq Scan。推定100行、実測20,000行、loops 1、フィルタ除外980,000行 |
| 計画の採取元 | ステージングの代表テナント1件で実測。generic/customのモードは未記録 |
| 不足する根拠 | 他のテナントの分布、統計の鮮度、更新負荷、索引容量の見積もり |

対象SQLの形は次のとおりです。

```sql
SELECT id, tenant_id, status, created_at
FROM public.orders
WHERE tenant_id = $1 AND status = 'pending'
ORDER BY created_at DESC;
```

この計画にはLIMITや途中で打ち切られたスキャンはありません。この例ではAPIが結果全体を必要とし、
返却結果の仕様を変える場合は別途判断します。

## プロンプト

```text
$postgres-performance-diagnostics を使い、注文検索APIを調査してください。
同じ600秒間の統計before.jsonとafter.json、取得済みplan.json、schema.sql、
アプリの応答時間の計測結果を提供します。入力の内容は上の根拠表とSQLのとおりです。

区間内の影響でSQLを順位付けし、観測事実と原因の仮説を分けてください。
行数推定の誤差と、索引を比較試験する価値があるかを説明してください。
計画は1テナントの例として扱い、generic/customは不明のままにしてください。
優先度、根拠、不確実性、変更コスト、検証計画を含むレポートを作ってください。
提供済みの根拠を先に使い、この依頼ではSQLの実行やDDLの適用は行わないでください。
```

## 結果の例

**優先候補は注文検索SQLです。** 観測したtop-level SQLの実行時間に占める割合は、
180,000 / 300,000 = **60%**です。
区間平均は180,000 / 900 = **200 ms/回**です。別途計測したアプリのp95は420 msで、
目標を超えています。SQLの平均値からリクエストのパーセンタイルやAPIの遅延全体は説明できません。

スキャンの実測行数は20,000 / 100 = **推定の200倍**です。
この実行では1,000,000行のうち980,000行をフィルタで除外しています。
統計とアクセス方法を調べる根拠になりますが、Seq Scan全般が非効率という意味ではありません。
また、`$1`の存在からgeneric planとは確定できません。

| 候補 | 根拠と残る不確実性 | 次の確認 |
| --- | --- | --- |
| 統計またはデータの偏り | 推定誤差が大きい。鮮度とtenant/statusの分布は不明 | 列統計・拡張統計、ANALYZE履歴、代表テナントを確認する |
| `(tenant_id, status, created_at DESC)`のB-tree | 等価条件と並び順に対応し、現在は`id`の索引のみ | ステージングで計画と総時間を比較し、heap参照・転送時間も確認する |
| 大量の結果返却 | この実行は20,000行を返す | ページングや列削減を提案する前に、利用範囲と転送コストを確認する |

索引は**比較試験の候補**であり、効果は未測定です。容量、更新時の追加処理、WAL、
作成負荷を確認して適用方法を選びます。統計の更新や拡張統計の追加も、
調査結果に応じて判断します。本番DDLの適用や性能改善の達成は報告しません。

## 次の検証

1. 適切なロールで対象relationと統計を調べ、可視性不足と統計不足を区別します。
2. 通常のテナントと偏りの大きいテナントを、同じデータ・パラメータ・キャッシュ条件で比較します。
   計画の採取元を記録し、結果の同値性も確認します。
3. 変更を1つずつ分け、前後のAPI p95、処理量、SQL区間時間、バッファ、更新・WALコストを測ります。
   応答時間や更新負荷が退行した場合の切り戻し条件を決めます。
